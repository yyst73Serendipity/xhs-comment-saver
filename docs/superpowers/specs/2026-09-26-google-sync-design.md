# Google 账号云同步设计

## 目标

为 `xhs-comment-saver` 增加独立 Firebase 项目支持，使用户继续通过 Chrome 的“加载未打包的扩展程序”使用扩展，并能在不同电脑和浏览器中通过同一个 Google 账号恢复收藏评论、分类、私人笔记和 AI 总结。

本次改造保持现有三栏管理页、评论收藏流程、分类管理、AI 总结和成长视图，不增加帖子或评论导航轨道。

## 已确认的产品决策

- 使用独立 Firebase 项目，不复用 `x-note-saver` 的 Firebase 项目。
- 扩展保持 Manifest V3 和原生 HTML、CSS、JavaScript，不引入前端框架。
- Firestore 保存结构化文本和媒体 URL，不上传图片、音频文件和分享卡片图片。
- `chrome.storage.local` 继续作为本地工作副本，支持快速读取和离线编辑。
- 大模型 API Key、`.env` 和 `apiconfig.json` 只保存在本机，不进入云同步。
- 所有业务数据修改统一经过后台存储入口，管理页和内容脚本不直接写业务存储键。
- 访客数据只有在用户预览并确认后才迁移到登录账号。
- 导入数据进入统一操作队列；清除本机缓存与删除全部云端数据是两个独立操作。

## 方案选择

### 采用：独立 Firebase 项目

独立项目分别管理 Authentication、Firestore、Hosting 和安全规则，避免从 `x-note-saver` 仓库部署规则时意外撤销本扩展的访问权限。Firebase 项目 ID 是部署环境配置，不写死在数据模型中；创建项目后写入本机 Firebase 配置并生成可提交的公开 Web 配置。

### 未采用：复用 `x-note-saver` Firebase 项目

复用项目虽然减少一次控制台配置，但两个仓库必须维护完全一致的组合规则，任何一次旧规则部署都可能让另一款扩展停止同步。

### 未采用：`chrome.storage.sync`

该存储方式不适合评论正文、媒体 URL 和 AI 总结组成的数据量，也没有本设计需要的事务、增量拉取、删除墓碑和冲突处理能力。

## 总体架构

系统由五个边界清晰的模块组成：

1. **账号认证**：Firebase Authentication 完成 Google 登录，Hosting 页面作为扩展外认证桥接，offscreen 文档承接 Manifest V3 登录流程。
2. **本地存储**：按访客空间和 Google UID 分区保存工作区、同步队列、游标和界面读取投影。
3. **数据模型**：把评论、分类、总结和设置转换成带版本、删除状态及冲突信息的记录。
4. **同步引擎**：本地修改先落盘，再异步提交 Firestore；按更新时间和文档 ID 分页拉取远端变化。
5. **界面适配**：管理页显示账号和同步状态，现有评论与分类界面继续读取兼容投影。

Service Worker 可以随时终止，因此账号状态、待上传操作和同步游标必须全部持久化。任何网络请求都不能阻塞本地收藏操作。

## 本地状态模型

根状态使用版本化结构：

```text
state
├── version
├── activeUid
├── user
├── guest
│   ├── remote
│   ├── pending
│   └── cursors
├── accounts
│   └── {uid}
│       ├── remote
│       ├── pending
│       └── cursors
├── migrated
└── status
```

每个工作区包含以下记录集合：

- `comments`：评论正文、作者、帖子信息、媒体 URL、评论组、分类 ID、私人笔记。
- `categories`：稳定分类 ID、名称和元数据。
- `summaries`：以分类 ID 为键的手写或 AI 总结。
- `settings`：分类顺序及与同步有关的非敏感设置。

为了保持现有界面工作，后台每次更新状态时同时生成 `xhs_comments`、`xhs_categories` 和 `xhs_summaries` 兼容投影。投影只供读取，所有写操作必须通过后台消息入口。

## Firestore 数据结构

独立 Firebase 项目使用以下路径：

```text
users/{uid}/comments/{commentId}
users/{uid}/categories/{categoryId}
users/{uid}/summaries/{categoryId}
users/{uid}/settings/main
users/{uid}/operations/{operationId}
```

业务文档统一包含：

```text
data        业务字段映射
revision    正整数版本号
deleted     删除墓碑
conflicts   尚未解决的冲突版本
updatedAt   Firestore 服务端时间
```

操作回执包含目标集合、记录 ID 和服务端创建时间。同步重试先检查回执，已经提交的操作不会重复应用。

## 稳定标识

### 评论

- 存在小红书 `commentId` 时，以规范化后的 `commentId` 作为记录身份。
- 缺少 `commentId` 时，根据规范化帖子 URL、作者和正文组合键生成确定性 SHA-256 标识。
- 原有本地 `id` 保留在迁移元数据中，但不作为跨设备去重依据。

因此两台设备同时收藏同一条评论时会写入同一文档，而不会生成两条记录。

### 分类

- `未分类` 使用固定 ID `uncategorized`。
- 其他默认分类和自定义分类使用稳定 ID。
- 评论保存 `categoryId`，不再以分类名称建立关系。
- 分类重命名只修改分类文档，不批量改写评论。
- AI 总结以 `categoryId` 关联，分类改名后仍然保留。

### 评论组

批量收藏继续生成稳定的 `groupId` 和 `groupIndex`。组信息用于管理页聚合，不作为评论唯一标识。

## 认证流程

1. 管理页发起 Google 登录请求。
2. Service Worker 创建 offscreen 文档。
3. offscreen 文档加载独立 Firebase Hosting 登录页。
4. Hosting 页面调用 Firebase Google 登录并把结果发送回扩展。
5. 扩展校验消息来源、扩展来源和请求 ID，拒绝过期或不匹配的响应。
6. 登录成功后激活对应 UID 的本地命名空间并开始拉取。

Manifest 保留固定 `key`，确保不同电脑加载同一份构建产物时得到相同扩展 ID。Hosting 登录桥接页只接受该固定扩展来源发出的请求。

## 数据写入与同步流程

### 本地修改

1. 内容脚本或管理页向 Service Worker 发送业务动作。
2. 后台校验输入并生成唯一操作 ID。
3. 数据模型把操作合并到本地记录并写入持久队列。
4. 本地状态和兼容投影在同一次存储提交中保存。
5. 界面立即得到成功结果，不等待网络。
6. 登录状态下触发后台同步；访客状态下只修改访客空间。

### 上传

1. 同步引擎按创建顺序读取当前 UID 的待上传操作。
2. Firestore 事务读取操作回执和目标记录。
3. 没有回执时合并字段、增加版本并写入服务端时间。
4. 同一事务写入回执。
5. 本地仅移除已经确认的操作，并重放其后的本地操作，避免覆盖上传期间产生的新修改。

### 下载

1. 各集合按 `updatedAt` 和文档 ID 排序分页拉取。
2. 相同边界时间允许安全重读，由版本号和 ID 去重。
3. 远端记录先写入账号工作区，再重放未上传的本地操作。
4. 保存分页游标并更新兼容投影。

### 自动触发

- 登录成功后同步。
- 本地业务修改后同步。
- 用户点击“立即同步”时同步。
- `chrome.alarms` 周期性补偿同步。
- 浏览器恢复联网后，下一次触发继续处理持久队列。

## 冲突规则

- 不同字段的并发修改按字段合并。
- 同一私人笔记被两台设备同时修改时，保留当前版本和冲突版本，交给用户选择或合并。
- 同一 AI 总结被并发编辑时采用相同的冲突保留方式。
- 分类重命名使用稳定 ID，不影响评论归属。
- 删除操作写入墓碑；旧版本离线编辑不能复活已经删除的记录。
- 用户重新收藏已删除评论属于显式恢复，会创建高于墓碑的版本。

## 旧数据迁移

首次读取旧版 `xhs_comments`、`xhs_categories` 和 `xhs_summaries` 时，只生成迁移候选，不立即上传。

登录后显示迁移预览：

- 本地评论数量。
- 新增评论数量。
- 重复评论数量。
- 分类数量。
- AI 总结数量。
- 私人笔记及总结冲突数量。

用户确认后，迁移记录转换为当前账号的操作队列。迁移完成标记按 UID 保存；中途中断可以继续，原始数据保留到云端确认完成后。用户取消时，访客数据继续保存在本机。

## 导入、清理和退出登录

- JSON 导入继续提供预览；确认后通过后台统一导入入口合并，登录状态下进入同步队列。
- “清除本机缓存”只删除当前账号的本地云快照与游标，保留身份信息；随后重新从 Firestore 下载。
- “删除全部数据”逐条生成评论、分类和总结墓碑并同步，不能复用清缓存操作。
- 退出登录只停止该账号同步并切换到访客空间，不删除本地或云端数据。
- 导出继续包含评论、分类和总结，作为独立于 Firebase 的人工备份。

## 管理页变化

在现有页面顶部增加账号同步区，保持三栏布局不变。该区域提供：

- Google 登录入口或当前账号邮箱。
- 本地模式、待同步、同步中、已同步和错误状态。
- 待上传操作数量与上次成功同步时间。
- 立即同步。
- 清除本机缓存。
- 退出登录。
- Firebase 配置帮助。

同步错误使用中文提示并保留本地功能。暂不增加评论导航轨道。

## 安全设计

- Firestore 规则要求请求已认证，并且路径 UID 与 `request.auth.uid` 相同。
- 私人未发布扩展额外配置唯一所有者 UID，其他 Firebase 用户即使完成 Google 登录也不能读写。
- 规则限制允许访问的集合、字段集合、字段类型和版本范围。
- Firestore 写入使用服务端时间，不信任客户端 `updatedAt`。
- 外部消息校验来源、请求 ID 和有效期。
- Firebase Web 配置可以公开；所有者 UID、项目 ID 和扩展 ID 不是服务器密钥。
- 大模型 API Key 不进入 Firestore、日志、导出扩展包或版本库。

## 错误处理

- 未配置 Firebase：保持本地模式并显示配置帮助。
- 网络中断：本地写入成功，队列保留并等待重试。
- 登录失效：停止云请求，保留队列并提示重新登录。
- 权限拒绝：显示账号或规则配置错误，不清除本地数据。
- Firestore 配额或服务错误：使用退避重试，手动同步仍可重新触发。
- 导入格式错误：在产生任何写入前拒绝整个文件。
- 单条评论或总结超过边界：在本地入口给出中文错误，不允许阻塞整个同步队列。

## 测试策略

### Node 单元测试

- 旧数据迁移、稳定 ID 和分类 ID 转换。
- 同评论跨设备去重。
- 不同字段合并、私人笔记冲突、AI 总结冲突。
- 删除墓碑与显式恢复。
- 上传确认后保留后续本地修改。
- 登录 A、退出并登录 B 时数据和队列隔离。
- 导入、清空、分类变更和总结保存全部经过统一队列。
- 未配置 Firebase 时继续本地工作。

### Firebase Emulator 集成测试

- 未登录请求被拒绝。
- 非所有者 UID 被拒绝。
- 所有者只能读写自己的路径。
- 非法字段、非法集合和错误时间戳被拒绝。
- 重复操作不会重复提交。

### 浏览器验收

- 保留现有评论收藏、分类、笔记、AI 总结和成长视图功能。
- 真实 Google 登录成功。
- 两个浏览器配置文件之间完成上传和下载。
- 断网收藏后恢复联网可以补传。
- 清除本机缓存后能够从云端恢复。
- 导入数据能够上传到云端。
- 页面没有新增评论导航轨道。

## 依赖与构建

新增依赖沿用已验证的 `x-note-saver` 技术栈：

- `firebase`：Authentication 和 Firestore Lite 客户端。
- `esbuild`：把 SDK 打包为符合扩展 CSP 的本地脚本。
- `firebase-tools`：部署 Hosting、Firestore 规则和运行 Emulator。
- `@firebase/rules-unit-testing`：连接真实 Emulator 验证规则，不模拟规则返回。

构建输出到 `dist/extension` 和 `dist/hosting`。源码根目录仍可用于开发，但最终验收统一加载 `dist/extension`，避免浏览器执行未打包的模块依赖。

## 实施边界

本次只完成 Google 登录、账号隔离、旧数据迁移、本地优先同步、冲突处理、账号状态界面、规则、构建、测试和文档。以下内容不在范围内：

- 评论导航轨道。
- 上传或代理小红书图片、音频。
- 多人共享收藏库。
- 手机 App。
- Firebase 以外的云存储后端。
- 对现有管理页进行无关的视觉重构。

## 完成标准

1. 新设备使用相同 Google 账号登录后，能够恢复评论、分类、私人笔记和 AI 总结。
2. 访客数据未经确认不会进入账号空间。
3. 本地修改不等待网络，离线队列在 Service Worker 重启后仍然存在。
4. 两台设备同时收藏同一评论不会产生重复记录。
5. 删除墓碑阻止离线旧修改复活记录。
6. 不同账号的数据、队列和同步结果互不影响。
7. 导入数据会同步；清除本机缓存不会删除云端数据。
8. API Key 和本机敏感配置不会上传或提交。
9. 单元测试、Firestore Emulator 测试、扩展构建和浏览器双端验收全部通过。
10. README 和 Firebase 配置文档与最终行为一致。
11. 管理页保持现有三栏结构，且没有评论导航轨道。
